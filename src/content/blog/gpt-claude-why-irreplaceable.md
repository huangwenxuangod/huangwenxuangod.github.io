**那天我对着 GPT 的输出发呆，屏幕上是一堆漂亮但完全没用的废话。**

我想做一个定时日报项目，需求其实很明确：每天固定时间自动抓取我的工作记录，整理成日报，然后发给指定邮箱。

GPT 答应得特别痛快，“没问题！这个简单！”，然后给我列了一堆技术栈，写了一段看起来很美的代码。

结果一运行，全是错的。

***

## 核心结论

Claude 不可替代的地方，不是它永远比 GPT 或 Gemini 更聪明，而是它在“做项目”这个场景里更像一个靠谱工程师：先确认需求，再补全上下文，最后给出能运行、能部署、能排错的完整方案。GPT 更擅长创意、表达和润色，Gemini 更适合搜索、总结和多模态信息处理，但当任务有明确成功标准，比如写代码、搭自动化流程、排查错误、把一个想法落地成项目时，Claude 的优势会被放大。

这篇文章回答三个问题：

- 为什么同一个定时日报项目，GPT 和 Gemini 没做成，Claude 做成了？
- 做项目时，应该如何判断一个 AI 模型是不是真的靠谱？
- 普通人应该怎样分配 Claude、GPT、Gemini 的使用场景？

## 一句话判断：什么时候必须优先用 Claude？

当你的任务需要“真正交付结果”时，优先用 Claude。这里的结果不是一段好看的回答，而是能运行的脚本、能部署的配置、能复现的流程、能排查的错误路径，以及你照着做之后真的完成了某件事。比如自动化日报、个人博客、数据清洗脚本、GitHub Actions 工作流、产品原型、复杂文档重构，这些任务都不只是聊天，而是工程执行。

我的判断标准很简单：如果一个 AI 只是让你觉得“它说得挺对”，但你做完以后事情还是没成，它就是顾问型工具；如果一个 AI 能主动追问缺失信息，把风险点提前指出来，并给你一套可以执行到最后的步骤，它才是执行型工具。Claude 在这次定时日报项目里，就是后者。

## GPT、Gemini、Claude 适合什么场景？

| 模型 | 更适合 | 不适合 | 我的用法 |
|---|---|---|---|
| GPT | 文案、标题、创意、润色、故事表达 | 需要强执行闭环的项目 | 用来想选题、改标题、让文字更生动 |
| Gemini | 搜索信息、总结资料、理解图片/视频 | 复杂代码项目和多步骤部署 | 用来快速了解事实、总结长内容 |
| Claude | 写代码、做项目、排错、长上下文分析、流程落地 | 纯娱乐式创意发散 | 用来推进真实项目和复杂任务 |

这张表不是评测结论，而是我的实际使用分工。模型能力会变化，但使用场景的判断逻辑不会变：创意任务看表达，信息任务看检索，项目任务看交付。

## 我用 GPT 做定时日报项目，失败了

**我那天才意识到，GPT 更像一个只会说漂亮话的销售，而不是能帮你解决问题的工程师。**

事情是这样的：我需要一个定时日报工具，已经想清楚了大概的逻辑，用 GitHub Actions 定时运行，读取我 Obsidian 里的每日笔记，提取关键内容，整理成 Markdown，然后用邮件发出去。

我把这个需求告诉 GPT，它的第一反应是：“太棒了！这个想法太实用了！我来帮你实现！”

然后它开始输出：

- 先给我列了 5 个“核心优势”
- 又给我画了一个“系统架构图”，但只是文字描述
- 接着写了一段 Python 代码，看起来很专业
- 最后告诉我“这样就搞定了”

我满心欢喜地复制代码去运行，结果报错。我把错误信息发给它，它说“这个小问题，我来修”，然后又给我一段新代码。

就这样反复了 5 次，每次都有新的错误。

最后我放弃了。

**GPT 不是在帮我解决问题，它是在表演“帮我解决问题”。**

## 换 Claude 试试，结果完全不一样

**我本来没抱希望，只是想着换个模型试试，结果 Claude 的第一句话就让我愣住了。**

我把同样的需求发给 Claude，甚至连措辞都没改。

Claude 没有说“太棒了”，也没有立刻给我写代码。

它的第一句话是：“在开始之前，我需要先确认几个细节，这样才能给你一个真正能用的方案。”

然后它问了我 7 个问题：

1. 你的 Obsidian 每日笔记是放在哪个文件夹？文件名格式是什么？
2. 你想提取笔记里的哪些内容？是全部内容，还是有特定的标题或标签？
3. 定时运行的频率是怎样的？每天几点？
4. 邮件发给谁？用什么邮箱发？
5. 日报的格式有什么要求吗？有没有模板？
6. 如果某天没有笔记，是跳过还是发空的？
7. 你对技术栈有偏好吗？还是我来选最合适的？

我一个一个回答完，大概花了 3 分钟。

然后 Claude 说：“好的，现在我清楚了。我给你一个完整的方案，包括代码、配置、以及每一步怎么部署。”

它给我的东西：

- 一个完整的 Python 脚本，注释清晰
- GitHub Actions 的配置文件，直接能用
- 每一步的部署说明，从创建仓库到设置 Secrets
- 几个常见问题的解决方案
- 如果出了问题，怎么排查

我照着做，一次就成了。

那天我盯着屏幕看了很久，第一次觉得：**这才是 AI 该有的样子。**

## 这不是偶然，是底层逻辑的区别

**那天的对比太强烈了，我开始思考：为什么三个模型的表现会差这么多？**

不是 GPT 和 Gemini 完全不能用，而是它们的底层目标不一样。

GPT 想的是：“怎么让用户觉得我很厉害？怎么让用户开心？”

所以它会先赞美你，给你看漂亮的架构图，说一堆你想听的话。至于最后能不能成，那是次要的。

Claude 想的是：“怎么帮用户把这件事做成？”

所以它会先问清楚细节，补全你没说出来的信息，然后给你一个真正能落地的方案。

一个偏表演型，一个偏做事型。

这就是我后来判断 AI 工具的核心标准。

## 测试场景：我要做一个定时日报项目

这个测试场景之所以有代表性，是因为它同时包含了文件读取、定时任务、邮件发送、GitHub Actions、Secrets 配置和异常处理六个环节。一个模型如果只能写出一段像样的脚本，却不能主动确认文件路径、时间时区、发件方式、空数据策略和部署细节，它在真实项目里就不算可靠。所以我故意只给了一句需求，想看它们会不会先补齐关键条件，而不是急着表演“我会写代码”。

我发出去的需求原文只有一句：

> 我想做一个定时日报项目，每天固定时间自动抓取我的 Obsidian 每日笔记，整理成日报，然后发邮件给指定邮箱。帮我实现一下。

就这么简单，没有更多细节。

我想看看，三个模型分别会怎么反应。

## GPT 的表现：过度谄媚，一堆废话，一到执行就拉胯

**GPT 的回答让我感觉像是在跟一个服务员说话，而不是在跟一个工程师讨论技术问题。**

它的第一句话是：“这是一个非常棒的想法！自动化日报可以帮你节省大量时间，让你更专注于工作本身！我完全理解你的需求，这就来帮你实现！”

然后它开始输出：

### 第一步：给我画饼

- “这个系统有以下 5 个核心优势……”
- “它将彻底改变你的工作流程……”
- “你会爱上这种自动化的感觉！”

### 第二步：给我看“架构图”

- “系统分为三层：数据层、处理层、通知层……”
- “每个层之间通过解耦的方式连接……”
- “这样设计的好处是扩展性极强……”

### 第四步：告诉我“这样就搞定了”

真正的问题，不是 GPT 说了“这样就搞定了”，而是它在关键变量根本没有落地之前，就把一个半成品包装成了可交付结果。像文件路径、SMTP 服务、邮箱授权码、GitHub Secrets、定时区和空笔记处理策略，这些决定项目能不能跑通的细节，它一个都没有兜住。结果就是我每报一次错，它就修一个表面问题，但前面没问清楚的债还在，所以修到第五次，项目依然没成。

对做项目的人来说，这类回答的风险很高，因为它制造的是“已经完成”的错觉。你会以为自己只差最后一步，实际上却还停留在需求没澄清、环境没对齐、交付没闭环的阶段。

## Gemini 的表现：中庸，但同样在关键环节掉链子

**Gemini 的问题不在于完全不会做，而在于它能交出一个七成像样的方案，却很少主动把剩下那三成最关键的条件问清楚。** 对检索、总结、资料概览类任务，这不算致命；但对自动化项目来说，恰恰就是那三成细节决定你到底能不能上线。

它没有说那么多漂亮话，直接开始给方案。

但是：

- 它假设我的 Obsidian 笔记在 `~/Documents/Obsidian/Notes/` 文件夹
- 它假设文件名格式是 `YYYY-MM-DD.md`
- 它假设我想提取整个文件内容
- 它假设我用 Gmail 发邮件
- 它假设邮件发给自己

这些假设没有一个是对的。

我把这些问题告诉它，它说“好的，那你修改一下这些变量就可以了”，然后给我列了一堆变量让我自己改。

问题是，我不知道有些值应该怎么填。比如 GitHub Actions 里的 Secrets 怎么设置？邮件服务器的端口是多少？

我继续问，它的回答就开始模糊了：“这个你可以去查一下文档”“不同的邮箱提供商可能不一样”。

最后我还是没搞定。

**Gemini 像是一个刚入行的实习生，能干活，但需要你把每一步都告诉它，而且关键时刻顶不上去。**

## Claude 的表现：先问问题，补全细节，直接搞定

**Claude 的第一句话就让我知道，这个模型不一样。**

它没有赞美，没有画饼，直接问：“在开始之前，我需要先确认几个细节，这样才能给你一个真正能用的方案。”

然后它问了我 7 个问题，我一个一个回答：

- 文件夹是 `D:/Obsidian/Vault/每日笔记/`，文件名格式是 `YYYY年MM月DD日.md`
- 只提取标题为“今日完成”和“明日计划”的部分
- 每天晚上 22:00 运行
- 用我的 163 邮箱发，发给我的 Gmail
- 格式就是简单的 Markdown，不需要太复杂
- 如果没有笔记，就发“今日无记录”
- 技术栈你选，简单稳定就行

回答完之后，Claude 说：“好的，现在我清楚了。我给你一个完整的方案，直接照着做就能用。”

然后它给了我三样东西：

### 第一样：完整的 Python 脚本

```python
import os
import re
import smtplib
from datetime import datetime
from email.mime.text import MIMEText
from email.mime.multipart import MIMEMultipart

VAULT_PATH = "D:/Obsidian/Vault/每日笔记/"
EMAIL_FROM = "your-email@163.com"
EMAIL_TO = "your-email@gmail.com"
EMAIL_PASSWORD = "your-email-password"


def get_note_path():
    today = datetime.now()
    filename = f"{today.year}年{today.month:02d}月{today.day:02d}日.md"
    return os.path.join(VAULT_PATH, filename)


def extract_content(note_path):
    if not os.path.exists(note_path):
        return "今日无记录"

    with open(note_path, "r", encoding="utf-8") as f:
        content = f.read()

    result = []
    sections = ["今日完成", "明日计划"]

    for section in sections:
        pattern = rf"#+\s*{section}\s*\n(.*?)(?=\n#+|$)"
        match = re.search(pattern, content, re.DOTALL)
        if match:
            result.append(f"## {section}\n{match.group(1).strip()}")

    return "\n\n".join(result) if result else "今日无记录"


def send_email(subject, body):
    msg = MIMEMultipart()
    msg["From"] = EMAIL_FROM
    msg["To"] = EMAIL_TO
    msg["Subject"] = subject
    msg.attach(MIMEText(body, "plain", "utf-8"))

    with smtplib.SMTP_SSL("smtp.163.com", 465) as server:
        server.login(EMAIL_FROM, EMAIL_PASSWORD)
        server.send_message(msg)


def main():
    note_path = get_note_path()
    content = extract_content(note_path)
    today = datetime.now().strftime("%Y年%m月%d日")
    subject = f"日报 - {today}"
    send_email(subject, content)
    print(f"日报发送成功: {subject}")


if __name__ == "__main__":
    main()
```

这段代码是**真的能运行**的，每一个环节都写实了，没有 `pass`。

### 第二样：GitHub Actions 配置文件

```yaml
name: Daily Report

on:
  schedule:
    - cron: '0 14 * * *'

jobs:
  send-report:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout repository
        uses: actions/checkout@v4

      - name: Set up Python
        uses: actions/setup-python@v5
        with:
          python-version: '3.11'

      - name: Create note directory
        run: mkdir -p ./daily-notes

      - name: Run script
        env:
          EMAIL_FROM: ${{ secrets.EMAIL_FROM }}
          EMAIL_TO: ${{ secrets.EMAIL_TO }}
          EMAIL_PASSWORD: ${{ secrets.EMAIL_PASSWORD }}
        run: python send_report.py
```

连 cron 表达式都帮我算好了：UTC 14:00 对应北京时间 22:00。

### 第三样：保姆级部署说明

1. 创建一个新的 GitHub 仓库。
2. 把 Python 脚本保存为 `send_report.py`。
3. 把 GitHub Actions 配置保存为 `.github/workflows/daily-report.yml`。
4. 在仓库的 `Settings -> Secrets and variables -> Actions` 里添加三个 Secrets。
5. 把 Obsidian 每日笔记同步到仓库里的 `daily-notes/` 文件夹。
6. 提交推送，然后手动点一次 `Run workflow` 做验证。

我照着做，一次就成了。

## 核心差异 1：Claude 是工程师思维，GPT/Gemini 更像销售或顾问思维

工程师思维的目标是：**把事做成。**

销售或顾问思维的目标是：**让你觉得我很厉害。**

所以 GPT 会：

- 先赞美你，让你开心
- 给你看漂亮的架构图，让你觉得它很专业
- 写漂亮但不能用的代码，让你觉得它能力很强
- 出了问题就说“小问题，我来修”，让你觉得它很负责

而 Claude 会：

- 先问清楚细节，确保理解正确
- 不搞花里胡哨的东西，直接给解决方案
- 代码不一定最漂亮，但一定更强调能用
- 出了问题会告诉你为什么，以及怎么避免

**一个在乎表演，一个在乎结果。**

## 核心差异 2：先问清楚再动手，而不是上来就瞎猜

很多时候，你以为自己说清楚了，其实没有。

我那个定时日报的需求，听起来已经很明确了，但里面依然藏着一堆关键细节：

- 笔记放在哪个文件夹？
- 文件名格式是什么？
- 提取哪些内容？
- 用什么邮箱发？
- 没有笔记怎么办？

GPT 和 Gemini 选择了“猜”。

Claude 选择了“问”。

这看起来慢，其实是最快的方式。**先花 3 分钟问清楚，比花 1 小时反复修改强得多。**

## 核心差异 3：执行层碾压，真的能把事情做成

很多模型都能给你一个“大概方案”，但 Claude 能给你一个“直接能用的方案”。

这意味着：

- 代码里的每一个路径都是对的
- 每一个配置项都告诉你怎么填
- 每一个可能出错的地方都提前告诉你
- 甚至连测试方法都帮你想好了

你不需要是专家，你只需要照着做，就能成。

这也是我后来最看重的能力：不是“会不会说”，而是“会不会交付”。

## 核心差异 4：废话少，直接给结果

GPT 和 Gemini 的输出里，经常混着大量“听起来舒服但没帮助”的话：

- “这是一个非常棒的想法！”
- “这样做有很多好处！”
- “让我来帮你实现！”
- “这样就搞定了！”

这些话听着舒服，但对解决问题没有任何帮助。

Claude 的风格更像：

- “我需要确认几个细节……”
- “这是完整的方案……”
- “照着这几步做……”
- “如果出了问题，这样排查……”

简洁、直接、有用。

## 核心差异 5：上下文理解深度不在一个级别

Claude 真的能“理解”你在说什么，而不只是“匹配”关键词。

我说“定时日报”的时候，背后其实包含了很多没说出来的信息：

- 我用 Obsidian 记笔记
- 笔记有固定的文件夹和命名格式
- 我只需要笔记里的特定部分
- 我要每天自动发邮件
- 我可能不会设置 GitHub Actions
- 我可能不知道邮箱授权码是什么

Claude 会把这些隐含条件主动拉出来确认。

GPT 和 Gemini 往往能听懂你说的话，但读不懂你没说出来的话。

## 如果你要写文案、搞创意：GPT 依然很好用

说了这么多 Claude 的好话，不是说 GPT 一无是处。

GPT 特别适合：

- 写文案、写广告语
- 搞创意、想点子
- 写故事、写小说
- 把干巴巴的内容写得更生动

这些场景不需要“把事做成”，需要的是“说得好听”，而这正是 GPT 的强项。

## 如果你要快速搜信息、做总结：Gemini 也有位置

Gemini 最适合承担“先把事实找齐，再给我一个摘要”的任务，比如技术概念速查、长文概览、跨网页信息归纳和图片视频辅助理解。它的优势在于搜索入口和多模态处理，而不是把一个包含环境变量、定时任务和异常处理的工程链路从头跑通，所以我现在把它放在信息层，而不是交付层。

Gemini 的搜索基因很强，它特别适合：

- 快速搜索信息
- 总结新闻、文章
- 回答事实性问题
- 多模态任务，比如看图片、看视频

我有时候会用 Gemini 来快速查一个技术概念，或者总结一篇长文章，它确实比自己读快得多。

## 但如果你要真的解决问题、做项目、写代码：优先用 Claude

这就是我的结论：如果你要真的解决问题，Claude 是第一选择。

什么叫“解决问题”？

- 你要做一个项目，从 0 到 1 上线
- 你要写一段代码，能运行，能解决实际问题
- 你要分析一个复杂问题，得到可执行的结论
- 你要做一件事，这件事有明确的成功标准

这些场景下，Claude 的优势会非常明显。

## 我的日常搭配：三个模型各用在什么地方

我现在三个模型都在用，但用在不同场景：

### Claude：解决问题、做项目、写代码

- 做任何需要落地的项目
- 写需要真正运行的代码
- 分析复杂问题，找解决方案
- 任何有明确成功标准的事

### GPT：写文案、搞创意、润色

- 写文章标题、写广告语
- 想创意点子、想选题
- 润色文章，让它更生动
- 写故事、写小说

### Gemini：搜信息、做总结、多模态

- 快速搜索事实性信息
- 总结新闻、长文章
- 看图片、看视频
- 查技术概念、查资料

一句话总结：**用 Claude 做事，用 GPT 写文案，用 Gemini 搜信息。**

## 第一次用 Claude 怎么开始

**第一次用 Claude，我建议你从一个小任务开始。**

不要一上来就做很复杂的项目，先试试水，感受一下它的风格。

推荐的第一个任务：

- “我想写一个简单的 Python 脚本，读取当前目录下所有的 `.md` 文件，统计每个文件的字数，然后输出一个表格。”
- “我想整理一下我的文件夹，把所有的图片都移到一个单独的 `images` 文件夹里，帮我写一个脚本。”
- “我想把这篇文章翻译成英文，但不要太生硬，要自然一点。”

随便选一个，发给 Claude，看看它的反应。

你会很快感受到它和别的模型不一样的地方。

## 可以直接复制的 Claude 项目提示词模板

如果你想用 Claude 做项目，不要只说“帮我做一个 XXX”。更好的方式是把目标、背景、约束和成功标准一次性说清楚，然后允许 Claude 先问问题。

可以直接用这个模板：

```text
我想做一个 [项目名称]，目标是 [最终要达成什么结果]。

我的背景是：[你会什么、不会什么、希望多简单]。
现在已有条件是：[已有文件、已有工具、已有账号、已有代码]。
约束是：[时间、技术栈、部署环境、预算、不能接受的方案]。
成功标准是：[怎样才算做成，比如能运行、能定时、能发邮件、能生成页面]。

你先不要急着写代码。
请先帮我确认需求里缺失的信息，列出必须问我的问题。
等我回答完，再给我一个可以一步步执行的方案。
```

这个模板的关键不在于写得多长，而在于把 Claude 拉进工程师模式。你不是让它表演聪明，而是让它先补齐信息，再交付结果。

## 用 Claude 做项目的 5 步流程

我现在用 Claude 做项目，基本固定成 5 步：

1. 先说目标，不急着说技术方案。
2. 让 Claude 先问问题，把隐藏条件补全。
3. 要求它给出最小可运行版本，而不是一上来做完整系统。
4. 每次只改一个环节，运行失败就把完整报错发回去。
5. 做成以后，让它帮你写部署说明、排错清单和下一步优化。

这套流程的好处是，它把 AI 从“回答机器”变成了“协作工程师”。你不用假装自己什么都懂，但你必须清楚自己要什么，以及什么结果才算成功。

## 怎么跟 Claude 提问效果最好

**跟 Claude 提问，有几个小技巧。**

### 技巧 1：把你的需求说清楚，但不用太细

- 好的提问：“我想做一个定时日报项目，每天固定时间自动抓取我的 Obsidian 每日笔记，整理成日报，然后发邮件给指定邮箱。”
- 不好的提问：“帮我写一个 Python 脚本，用 `smtplib` 发邮件，读取 D 盘某个文件夹里的文件……”

**把目标说清楚，细节让 Claude 来问你。**

### 技巧 2：告诉 Claude 你的背景

- 好的提问：“我是一个编程小白，想做一个个人博客，越简单越好，不要用太复杂的技术栈。”
- 不好的提问：“帮我做一个个人博客。”

**告诉 Claude 你是谁，它会给你更合适的方案。**

### 技巧 3：如果不满意，直接说

- 好的反馈：“这个方案太复杂了，我想要更简单的。”
- 不好的反馈：“哦，好吧。”

**Claude 会根据你的反馈调整，你越直接，效果越好。**

## 避坑：不要用跟 GPT 说话的方式跟 Claude 说话

很多人把 Claude 用不顺手，不是模型不行，而是输入方式还停留在“让 AI 给我一个漂亮答案”的阶段。跟 GPT 对话时，你可能会习惯先铺很多情绪、先求一个完整回答、先让它看起来理解你；但 Claude 在项目场景里更像协作工程师，它更吃“目标、约束、现状、成功标准”这些信息。你越直接，它越容易进入执行状态；你越把需求包装成模糊聊天，它越可能给出泛泛而谈的高层建议。

更实用的方式是：先讲你要做成什么，再允许它追问缺失信息，最后要求它按步骤给方案。这样你拿到的就不是一个“看起来很聪明”的回答，而是一套更容易跑通的执行链路。

## 进阶：如何发挥 Claude 的最大威力

如果你想发挥 Claude 的最大威力，这里有几个进阶技巧。

### 技巧 1：给它足够的上下文

如果你已经做了一部分工作，最有效的做法不是重新从零提问，而是把现状完整交代给 Claude。比如你可以直接说：你现在在做什么项目、已经完成到哪一步、卡在哪个报错、哪些约束不能改、你更在意速度还是稳定性。这样的上下文会直接改变它的输出质量，因为 Claude 不需要再凭空猜测你的环境和目标，而是能在真实边界内给出方案。对项目协作来说，上下文不是“附加说明”，而是能不能少返工的关键。

### 技巧 2：让它扮演某个角色

- “你现在是一个资深的前端工程师，有 10 年经验，帮我看看这个代码怎么优化。”
- “你现在是我的创业导师，帮我分析一下这个项目靠不靠谱。”

角色设定能让 Claude 的输出更聚焦。

### 技巧 3：让它先思考，再回答

- “你先别急着给答案，先分析一下这个问题有几种解法，每种解法的优缺点是什么，然后再给我推荐一个最合适的。”

让 Claude 先思考，能得到更深入的答案。

## 不是说 GPT/Gemini 不好，而是它们的定位不一样

再强调一遍：不是说 GPT 和 Gemini 不好。

它们也有自己的优势，也有自己适合的场景：

- GPT 适合写文案、搞创意
- Gemini 适合搜信息、做总结

但如果你要真的解决问题、做项目、写代码，Claude 依然是我最优先的选择。

## 选择模型的核心标准：能不能帮你把事做成

最后，给你一个选择模型的核心标准。

不要看评测分数，不要看参数多少，也不要只看谁更火。

只看一点：**它能不能帮你把事做成？**

如果能，就用它；如果不能，就换掉。

这就是我现在判断 AI 工具的方式。

## 常见问题

### Claude 一定比 GPT 强吗？

不一定。Claude 在做项目、写代码、长上下文分析和复杂任务拆解上更适合我，但 GPT 在文案、标题、创意表达上仍然很好用。真正重要的不是“谁更强”，而是任务类型和模型能力是否匹配。

### 为什么 GPT 看起来也会写代码，但项目还是容易失败？

因为写出一段像代码的文本，和交付一个能运行的项目，是两件完全不同的事。项目需要确认路径、权限、环境变量、部署方式、异常处理、测试方法和失败回滚。GPT 很容易在需求不完整时直接猜，而猜错一个关键假设，后面代码再漂亮也没用。

### Claude 做项目时最重要的习惯是什么？

最重要的习惯是让 Claude 先问问题。一个靠谱的工程协作，不是马上输出代码，而是先确认目标、输入、输出、环境、约束和成功标准。先问清楚，后面会少掉大量返工。

### 普通人应该怎么同时使用 Claude、GPT 和 Gemini？

我的分工是：Claude 用来做项目和解决问题，GPT 用来写文案和做创意，Gemini 用来搜信息和总结资料。不要让一个模型承担所有任务，也不要因为一个模型在某个场景失败，就否定它在其他场景的价值。
